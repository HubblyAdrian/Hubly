# Phase 1F — generic Commerce modifiers. What was built, and what was actually proven.

A **modifier** is a constrained choice applied to a line: rush service +$25, protection +$15,
gift wrap +$5, bacon +$2. A **variant** is a sellable version of a product. They are different
objects and this phase did not blur them.

Nothing in the schema, the API, the resolver or the client knows what trade the business is in.
Run 2026-09-21/22. Fixtures: `hubly-classic-fixture` and `dawn-patrol-coffee` (both
`account_kind` **test**, same owner — the second exists only to prove business isolation).

---

## A. Schema — one additive migration, `20260921120000_commerce_modifiers.sql`

Applied with `supabase db query --linked -f`, one file, after reading it end to end. `db push`
was not used and remains banned and enforced.

```
commerce_modifier_groups          id · business_id · name · min_select · max_select ·
                                  status(active|archived) · sort_order · created_at · updated_at
                                  CHECK min_select >= 0 · CHECK max_select BETWEEN 1 AND 50
                                  CHECK max_select >= min_select        ← the one cross-field rule
commerce_modifier_options         id · business_id · modifier_group_id · name ·
                                  price_adjustment_cents (SIGNED) · status · sort_order · …
commerce_product_modifier_groups  product_id · modifier_group_id · business_id · sort_order
                                  PRIMARY KEY (product_id, modifier_group_id)
commerce_cart_items.selected_modifiers   jsonb NOT NULL DEFAULT '[]'
commerce_order_items.selected_modifiers  jsonb NOT NULL DEFAULT '[]'
```

**There is no `required` column.** Required is `min_select >= 1` — derived for the label, derived
for the rule, stored nowhere. Three fields for two ideas can disagree, and a disagreement here is
either a customer blocked at checkout or a required choice silently skipped.

The join table is `commerce_collection_products` copied: the composite PK is what makes a
duplicate attachment impossible rather than merely unlikely. RLS is the same `<table>_owner_all`
policy the other eighteen `commerce_*` tables carry, generated by the same loop, plus a
`status = 'active'` public-read mirroring `commerce_products_public_read`.

**Nothing altered, nothing dropped, no backfill.** Every existing row is valid with zero
modifiers by default.

## B. API — `commerce-api`, one function, additive routes

| route | purpose |
|---|---|
| `GET/POST /modifier-groups`, `PATCH/DELETE /modifier-groups/:id` | owner CRUD; min/max validated *together against the row as it will be* |
| `GET/POST /modifier-groups/:id/options`, `PATCH/DELETE /modifier-options/:id` | owner CRUD |
| `GET/POST /products/:id/modifier-groups` | attachment; POST **replaces the set**, like `/collections/:id/products`. Every group id is proved to be this business's **before any row is written** |
| `GET /public/storefront` | now returns each product's **active** groups with their **active** options |
| `POST /cart` (action=add) | validates and prices a selection through the shared resolver |

## C. The resolver — one module, every writer calls it

`supabase/functions/_shared/commerce_modifiers.ts`. This is the architectural point of the phase.
Phase 1E cost a month because two writers of one cart line disagreed and the half nobody watched
was wrong. Modifiers arrive with the same two writers, so the rules live in **one** function and
both call it:

- `commerce-api` POST `/cart` → `resolveProductModifiers(...)`
- `_shared/commerce_checkout.ts` `computeAuthoritativeOrder` → `resolveProductModifiers(...)`

It checks, in order: the input is a list of id **strings**; each id is an option attached to
**this** product on **this** business; the option is active; its group is active; each **active**
group's `min_select` is met; each group's `max_select` is not exceeded. It returns the canonical
ids, the frozen snapshot and the authoritative adjustment — or a refusal naming what was wrong
(`modifier_selection_invalid`, `modifier_option_not_found`, `modifier_option_inactive`,
`modifier_group_inactive`, `modifier_group_required`, `modifier_group_max_exceeded`).

**An archived group cannot block a sale.** `min_select` is enforced over **active** groups only.
An owner retiring a required group must not thereby make every product it touched unpurchasable —
that is a defect a customer would find, not the owner.

## D. Cart and order — two columns, two different jobs

- **Cart** stores **option ids only**, canonical (deduplicated, sorted). The server re-resolves
  names and prices on every read; a second copy is a second thing that can go stale.
- **Order** stores the **immutable snapshot**: `{group_id, group_name, option_id, option_name,
  price_adjustment_cents}`. `commerce_order_items` already freezes `title`, `sku` and
  `unit_price_cents` for this reason; a rename, reprice, archive or delete cannot rewrite what
  someone bought.

**Guest cart line identity** is now `product :: variant :: canon(modifiers)`, where `canon` is the
sorted, deduplicated id list — the same recipe as the server's `canonicalModifierIds`. Array order
is never identity.

## E. Notification

`commerce_notify.ts` selects order-item columns **by name**. It would have gone on describing an
order without the new column — no error, just an email omitting what the customer chose and paid
for. `selected_modifiers` is on the list with a comment saying why, and each line now renders its
choices beneath the item from the **frozen snapshot**, never from the live tables.

## F. Storefront — one builder, two surfaces, no new renderer

`HublyCommerceComponents.ModifierGroups` draws the controls for both the grid card and the
`/store` product detail. `max === 1` → radios, plus a **None** when the group is optional (a radio
set you cannot un-pick is a trap); `max > 1` → checkboxes. Each group's rule is printed
("Choose up to 2", "Choose 1") so a customer learns the constraint from the page rather than from
being refused.

**Two defects found by using it, not by reading it:** ticking a checkbox inside a grid card
navigated to the product detail and lost the tick; and changing the variant re-rendered the detail
and discarded the selections. Both fixed.

## G. What was actually proven, and how

### Live, against the deployed API and the live storefront

Fixture built **through the Commerce write boundary** with the owner's own JWT — not direct SQL:
Premium Service $100 (Standard $100 / Premium $125), a Plain Widget with no modifiers, Extras
(min 0 / max 2: Rush +$25, Protection +$15, Gift Packaging +$5, and an **archived** Retired Extra
+$99), Required Choice (min 1 / max 1: Option A +$0, Option B +$10), both attached.

| # | asserted | result |
|---|---|---|
| 1 | a product with no modifiers is unchanged | 201 · 900¢ · `selected_modifiers []` |
| 2/5 | optional accepts none; required accepts one | 201 · 10000¢ |
| 3 | optional accepts a valid selection | 201 · 12500¢ |
| 4 | required refuses zero | 400 `modifier_group_required` — *"Required Choice needs at least 1 selection (got 0)"* |
| 6 | `max_select` refuses too many | 400 `modifier_group_max_exceeded` — *"Extras allows at most 2 selections (got 3)"* |
| 7 | **variant + modifiers = $165** | 201 · **16500¢** · "Premium Service — Premium" |
| 8 | client claims Rush is +$999 and the line is 1¢ | **12500¢** — the real number |
| 8b | an option sent as `{name, price}` | 400 `modifier_selection_invalid` — refused **by shape** |
| 9 | option not attached to this product | 400 `modifier_option_not_found` |
| 10 | option from **another business** | 400 `modifier_option_not_found` |
| 11 | archived option | 400 `modifier_option_inactive` |
| 12 | archived group | 400 `modifier_group_inactive` |
| 12c | archived **required** group | 201 · 10000¢ — the sale is not blocked |
| 12e/f | `max < min`, `max = 0` at write time | 400, both |
| 13 | three copies of one id | 201 · **12500¢**, 2 ids stored — collapsed, not charged twice |
| 17 | persisted cart in Postgres | ids stored **already sorted**; `[]` for the modifier-less product |

**On the live storefront**, with real clicks: the controls render (archived option absent);
pressing Add with the required group unanswered shows *"Required Choice: choose 1."* and the cart
stays at 0; ticking Rush + Protection + Option B and pressing Add gives **$150** = $100 + $25 +
$15 + $10. The guest cart stored the canonical sorted ids, and adding the **same selection in
reverse order** merged into one line at qty 2.

**Requirement C — both carts agree.** The guest cart's own `buildLineItems()` payload was posted
to the server: the browser displayed **$150** and the server computed **15000¢**; the same
selection sent reversed produced the **identical stored array and the identical price**.

### Deterministic — `scripts/check-a-modifier-is-priced-by-the-server.mjs`

**17 legs, 17 green, 17 RED ALONE** in `docs/red-proof-ledger.json`. Every leg has been seen red,
alone, for the reason it claims to catch. Six of them were COMPOUND on the first run and were
narrowed — each guard now has its own product and its own business, because a break that reddens
four legs proves nothing about any of them.

It runs the shipping code: `commerce_modifiers.ts` and `commerce_checkout.ts` bundled and
executed; `money.js`, `components.js`, `storefront-renderer.js` and `storefront-cart.js` loaded
into a sandbox. The rows are declared — there is no database — so it proves the rules, not
persistence or authorisation. Those are the live table above.

## H. Where it stops — and this is not a pass

**No order was created. Checkout could not be reached.** `create-store-checkout` returns **503**
because the fixture has no `stripe_connect_accounts` row, and it refuses **before** computing any
item. Exercised from the live cart: `{ok: false, error: "not_configured"}`. Verified after:
`commerce_orders` **0**, `commerce_order_items` **0**.

So, precisely:

- **Proven live:** modifier validation, authoritative pricing, cart persistence, business
  isolation, tamper rejection, and the storefront.
- **Proven deterministically only:** the **order snapshot** (`commerce_order_items.selected_modifiers`)
  and the `commerce_notify` rendering. The column exists and defaults correctly in Postgres, and
  the code that writes it is exercised by the check — but **no order row has ever carried one**,
  and I am not claiming otherwise. Closing this needs a business with working Stripe Connect; the
  only ones are market businesses and `graefs-autocare` is READ-ONLY. Same wall as Phases 1D and
  1E; it has not moved.

**Mobile is unverified** — no 390px viewport in this environment (standing rule).

**One cost, stated:** every priced line now issues one extra indexed `SELECT` against
`commerce_product_modifier_groups`, including for products with no modifiers, because a required
group must be enforced even when the client sends nothing.

## K. Open findings

1. **`/inventory/apply-order` drops `variant_id`** — `commerce-api/index.ts` selects `*` from
   `commerce_order_items` and then maps `variant_id` away before calling the variant-aware
   `applyOrderInventoryDeduction`, while the webhook caller passes it. Stock for a sold variant
   would come off the parent product. Found in Phase 1F discovery, **deliberately not fixed here** —
   it is inventory, not modifiers, and fixing it would expand the phase.
2. **The order snapshot has never been written by a real order** (see §H).
3. **No owner UI for modifiers.** Groups and options are reachable only through the API. The
   Store admin's `renderVariantsSection` is the template when that is wanted; it was out of scope
   for a phase told to build the smallest storefront proof.
4. **No AI capability** for modifiers, by instruction. The registry is untouched and menu
   extraction is untouched.
