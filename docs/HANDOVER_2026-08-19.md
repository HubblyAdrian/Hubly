## 2. What changed, by area

### 2.1 Page generation was failing ~37% of the time, silently

A person typed a sentence, watched a loading skeleton for 90 seconds, and no
site was ever built. No error, no signal, no record.

The first diagnosis — `EdgeRuntime.waitUntil` losing work when the isolate is
recycled — was **wrong**. The real cause was an OpenAI `429 insufficient_quota`;
the account had run out of credit. `hubly_ai.ts` collapsed every provider
failure into one string ("OpenAI is temporarily unavailable") and the handler
discarded the HTTP status, so quota exhaustion, a rotated key and a real outage
were indistinguishable.

Fixed regardless, because the *invisibility* was real whatever caused it:

- **`document_build_jobs`** (new table) — a row written *before* the build is
  dispatched. A job still `running` past `expected_by` is provably stuck.
- **`hubly-document-build`** (new function) — the build moved out of `waitUntil`
  into its own isolate, awaited. Explicitly **not** a queue; if that isolate
  dies the work is still lost. Real durability needs a worker outside the
  request path (pg_cron → `net.http_post`, or Supabase Queues). **Recommended
  follow-up.**
- **Retry with backoff in `hubly_ai.ts`** — there was none; a single 429 ended
  the turn. `retry-after` honoured; `insufficient_quota` deliberately *not*
  retried, because it is a billing state.
- **The client** stops the skeleton, explains, and offers Retry.

### 2.2 Facts the owner typed were being dropped

There was no extraction step. A phone number reached the business record only if
the model happened to call `updateDraft`. One real message carrying eleven facts
produced a record holding only the business name.

- **Tier A — patterns** (`_shared/hubly_extract.ts`): phone, email, postcode,
  state, priced services. No model, no cost, cannot decline to run.
- **Tier B — one pass with a REQUIRED schema**: city, address, service-area
  towns, hours, years, radius. Every key required and nullable, so each field is
  *considered* rather than optionally mentioned.
- Fills **blanks only** — corrections still go through `updateDraft`.
- Runs before `generateDocument` can be dispatched.

Six columns had **no writer at all** (`state`, `address`,
`service_area_cities`, `travel_radius_miles`, `years_in_business`,
`settings_business_hours`) — `patch_business_in_progress` is a whitelist and
they were not on it. A patch containing them returned `ok: true` and changed
nothing. Migration `20260819030000` adds them.

### 2.3 Generated sites all looked the same

The page header is chrome, so the generator could not vary it — it was
byte-identical on every site but for two initials.

`selectChromeVariant` picks between real layouts from real facts: logo aspect
ratio (measured from the asset's own header bytes), navigable section count,
whether the hero paints itself dark, and the trade read out of the business
**name** (`business_type` is a coarse bucket — a chimney sweep is categorised
"cleaning"). No randomness, so the same business always renders the same header,
which is what makes "put the logo in the middle" answerable.

### 2.4 Supabase key resolution

All 36 files now resolve credentials through `_shared/supabase_admin.ts`. Three
traps fixed, each of which would have broken silently:

1. **An empty key used to be tolerated.** Nine call sites did
   `(Deno.env.get("SUPABASE_SERVICE_ROLE_KEY") || "").trim()` and carried on with
   `""`, producing a 401 the caller logged and moved past. `requireSecretKey()`
   now throws.
2. **The Bearer header.** Every hand-rolled site sent
   `{apikey: key, authorization: Bearer key}`. Correct for a legacy JWT, **fatal
   for an `sb_secret_` key** — those are not JWTs and PostgREST rejects them as
   "Invalid JWT". Same 401 as the empty-key case, so indistinguishable in a log.
3. **`SUPABASE_PUBLISHABLE_KEY` is singular; the platform injects
   `SUPABASE_PUBLISHABLE_KEYS`.** All five fallbacks were dead code.

## 3. Things that will bite you

Ranked by how much time they cost this week.

1. **The repo is not the source of truth for the database.** A function body was
   rebuilt from a migration found by name; it was two revisions stale, silently
   reverted a validation block, and took down every draft write in production.
   Always: `grep -rln "create or replace function <name>" supabase/migrations/ | sort | tail -1`,
   and check `docs/schema.sql`.

2. **`create or replace` reports "Success. No rows returned" even when the body
   can never execute.** A plpgsql body is not planned until it is called. Verify
   a function by **calling** it, against a real row, reading the row before and
   after.

3. **Every Edge Function bundles its own copy of `_shared`.** Change a shared
   module and you must redeploy *every* function importing it, or you get new
   code in one function and old code in another with nothing failing. Use
   `npm run deploy:generation` for the build pair.

4. **`deno check` reports FEWER errors on a syntactically broken file.** A bad
   import split ten files; `deno check` scored three of them as *improved*. Only
   `supabase functions deploy`, which actually bundles, caught it.

5. **`verify_jwt` is set per-function in the dashboard, not `config.toml`.** Only
   19 of 49 functions are declared. The rest have mixed, invisible settings —
   `hubly-conversation` reaches its handler with *no credentials at all*, while
   `chatbot-message` is blocked at the gateway. Probe, do not read.

6. **A gateway 401 and a broken-credential 401 look identical from outside.**
   Always probe with a real JWT so the request reaches the handler.

7. **Policies created in the dashboard are invisible to any check runnable from
   the code.** Six policies dropped during the RLS sweep existed only live and
   cannot be diffed against what replaced them.

## 4. Outstanding — the API key migration

**Status: step 0 done and verified. Steps (b)–(e) outstanding. Legacy keys still
enabled and still in use.**

Context: the legacy `service_role` key and the database password were both
pasted into a chat transcript. That is why this migration is happening.
**Both should be rotated regardless of how far the migration gets.**

- [x] **0.** Refactor all key resolution; empty key throws. Verified with a full
      end-to-end build *before* any key changed, so a failure could only be the
      refactor. It caught one: see below.
- [ ] **b.** Replace the 7 hardcoded `anon` JWT literals with the publishable key
      `sb_publishable_YTqCIUFVzLYgJvYgGzJSEg_13YA-YzH`, as **one shared
      constant**, not seven copies. Files: `api/router.js`,
      `public/{get-done,hubly,marketplace-lite,marketplace-ops,platform-home,portal}.html`.
      Verified safe: the publishable key is accepted by the gateway and by
      PostgREST in every header shape tested.
- [ ] **c.** Redeploy **every** Edge Function (see §3.3).
- [ ] **d.** Full gate: draft → facts extracted → logo uploaded and serving →
      build dispatched → `running → succeeded` → document lands → page renders
      logo and phone. Plus confirm all 7 pages still authenticate.
- [ ] **e.** Disable legacy keys — **only after (d) passes.**

### One known defect blocking a clean (e)

**`booking-notify` will break.** `_shared/booking_notify_call.ts` calls it with
`adminHeaders()`, which correctly omits `Authorization` for a non-JWT secret key,
into a gateway that requires one. Same failure as `hubly-document-build` had.

Fix: `verify_jwt = false` on `booking-notify` plus an in-function credential
check. Not a weakening — the gateway asks "is this a well-formed JWT", the
handler would ask "is this *our* key".

**This is reasoned, not demonstrated.** Triggering it needs a real confirmed
booking, which was never produced.

### What step 0's verification caught

The end-to-end build failed with `running → stalled`. `SUPABASE_SECRET_KEYS` was
*already* populated with a real `sb_secret_` key, so inverting the precedence to
new-key-first made the system use it immediately — and
`hubly-document-build`'s `verify_jwt = true` meant the gateway rejected the
non-JWT credential before the handler ran.

Had the code sweep and the key creation happened together, this would have read
as *"the new keys broke the build"*, and rolling back the keys would have fixed
nothing.

## 6. Recommended next work

   transcript.

3. **Delete dead code.** `hire-crm`, `mission-control` and

   functions no one has ever used. Unclear whether that is by design or a
   regression.

   main product entry point, with no gateway check. Pre-existing and unrelated
   to the key work, but worth its own look.

   unrepresentable. Twelve call sites guard on `!= null`; they should move to
   `> 0`. See `KNOWN_ISSUES`.
