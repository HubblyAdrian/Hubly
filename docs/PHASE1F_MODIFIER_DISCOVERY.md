# Phase 1F — modifier discovery. No code was changed.

Read 2026-09-21 against the repo and the live database. Nothing here is implementation; every
number below was measured, and where a number contradicts an existing document, the document is
corrected rather than repeated.

---

## A. What modifier-like structures already exist?

Four. None of them is a Commerce modifier.

**1. `commerce_product_variants` — variants, not modifiers.** 10 columns, `price_cents` nullable,
`options jsonb`. A sellable unit with its own price and stock. Proven end-to-end in Phase 1E.
Note `options jsonb` is **written** by commerce-api and **returned** in the public payload and
**read by nothing** — a precedent for a jsonb nobody consumes, worth not repeating.

**2. `public.addons` — the relational table. Dead.** 6 columns: `id, business_id, name, price,
description, sort_order`. Measured live: **0 rows, 0 businesses.** No group, no constraints, no
product link. `hubly_capability_registry.ts:1214` records the decision to stop reading it —
*"editor-era tables… no writer anywhere in the conversational path"*.

**3. `meta.service_catalog.addons` — the living addon model, and it belongs to Offerings.**
`HublyAddon { id, name, description, price_cents, duration_delta_minutes, active, created_at,
updated_at }` (`_shared/service_engine.ts:21`), attached per-offering by
`HublyService.addon_ids: string[]`. Stored as JSON in `businesses.meta`, not in a table.
Measured live: **4 businesses carry a non-empty `service_catalog.addons`.** Flat — no groups, no
min/max, no required.

**4. Smart Quote `modifiers` — the only place Hubly already expresses constrained priced choice.**
`public/smart-quote/engine.js` defines a per-trade `modifiers` step whose answers become
`lineItems` of `kind:'modifier'`. It is priced server-side by `_shared/booking_price.ts`, which
imports the browser engine itself so the two can never drift. But it is **hard-coded config per
trade**, not entity data an owner creates, and it is bound to Offerings.

> **Correcting the record.** `docs/RESTAURANT_ARCHITECTURE_AUDIT.md` §3.1 states that
> *"`public.addons` … carries `duration_delta_minutes`, and `services.addon_ids` links it to
> Offerings"*. Measured against `docs/live-schema.md` and the live DB: the `addons` **table** has
> neither column, and `services` (10 columns) has **no `addon_ids`**. Both live in
> `meta.service_catalog` JSON. The audit's *conclusion* — addons cannot fill the modifier gap — is
> correct; the columns it names to justify it do not exist. A scar note is a memory of a
> measurement, not a measurement.

**Nothing anywhere carries a group, a required flag, or a min/max.** And
`commerce_cart_items` (11 columns) and `commerce_order_items` (12 columns) have **no jsonb and no
column of any kind for a selection**. An order cannot record "no onions" today. That is the gap.

## B. Why the addons system cannot be reused

Four independent reasons, any one of which is sufficient:

1. **Wrong store.** `service_catalog` is Offerings, held as JSON in `businesses.meta`. Commerce is
   relational tables. Attaching Commerce modifiers there would put product data in the Offerings
   store — a second representation of one thing, which is the two-stores disease already recorded
   in `SETTLED` #2 and already paid for once.
2. **Wrong shape.** Flat list. No group, no required, no min/max — the three things a modifier is.
3. **Wrong attachment.** `addon_ids` hangs off a service. There is no product attachment at all.
4. **Carries service semantics.** `duration_delta_minutes` is meaningless on a pizza topping, and
   a model that ships a dead field teaches the next reader that the field means something.

And the relational `addons` table is empty and explicitly abandoned.

**What should be reused from that world is the discipline, not the storage:** `priceBooking`
resolves add-ons *by id against the stored catalog* and takes no price from the request
(`booking_price.ts:154`). That is the same rule `computeAuthoritativeOrder` already applies to
variants, and it is the rule the modifier path must inherit.

## C. Where modifier groups and options should live

**New relational tables beside the other 18 `commerce_*` tables**, following their conventions
exactly: `uuid` PK, `business_id` FK + index, `sort_order int`, `created_at/updated_at`, RLS
enabled with the `<table>_owner_all` policy generated by the `do $$ … %I` loop at
`20260729120000_commerce_engine.sql:400`.

Proposed (names follow the existing convention, no restaurant vocabulary):

```
commerce_modifier_groups    id, business_id, name, required bool, min_select int, max_select int,
                            status text ('active'|'archived'), sort_order, created_at, updated_at
commerce_modifier_options   id, business_id, modifier_group_id, name, price_delta_cents int,
                            status text, sort_order, created_at, updated_at
commerce_product_modifier_groups  product_id, modifier_group_id, business_id, sort_order
                            PK (product_id, modifier_group_id)
```

**Not** `commerce_products.metadata` jsonb: unqueryable, no FK, no per-option RLS, and no stable
identity for an option. **Not** `variants.options` jsonb, for the same reasons plus the precedent
above. `price_delta_cents` is signed — a negative delta ("no cheese −$1") costs nothing to allow
and is the same field.

## D. How modifiers attach to Products

Through `commerce_product_modifier_groups`, which is **`commerce_collection_products` copied
exactly** — same composite PK, same `business_id` denormalisation, same `sort_order`. That table
already works, its ordering already survives the public read
(`commerce-api/index.ts:168` orders by `sort_order` and filters membership to the public product
set), and Phase 1E proved that ordering reaches the page.

Many-to-many on purpose: "Gift Wrap +$5" is defined once and attached to forty products. Group
order comes from the join's `sort_order`; option order from the option's own.

## E. Where selected modifiers live in the cart

**The two carts are not symmetrical, and only one of them is real.**

| | guest cart | persisted cart |
|---|---|---|
| where | `localStorage`, `storefront-cart.js` | `commerce_cart_items` |
| who writes it | the customer, on every real storefront | **nothing in `public/` — ever** |
| live rows | n/a | **0** |
| merges a repeat add | **yes**, on `lineKey` | **no** — `POST /cart` INSERTs unconditionally |

- **Guest cart:** add `modifiers: [optionId, …]` to the stored line object and fold a canonical
  form into `lineKey`. **No schema change.** This is the path a customer actually uses.
- **Persisted cart:** needs a column. Smallest additive choice is
  `selected_modifiers jsonb not null default '[]'` on `commerce_cart_items`, holding **option ids
  only** — identity, nothing else, because the server re-resolves names and prices on every read
  anyway. A child table (`commerce_cart_item_modifiers`) is more normalized but costs a table, a
  join on every cart read, and cascade handling, for a cart with zero rows and no client.
  Revisit only if per-modifier inventory ever arrives — an explicit non-goal.

## F. Where the order snapshot goes

`commerce_order_items` **is already the snapshot layer** — `title`, `sku` and `unit_price_cents`
are frozen there for exactly this reason, and the comment at `create-store-checkout/index.ts:136`
says so. Add one column in the same spirit:

```
selected_modifiers jsonb not null default '[]'
  -- [{ group_id, group_name, option_id, option_name, price_delta_cents }, …]
```

Ids for traceability, **names and prices frozen** so a later rename, reprice, archive or delete
cannot rewrite history. There is exactly one writer of `commerce_order_items`
(`create-store-checkout`), so this is one insert to extend.

> ⚠ **`commerce_notify.ts:238` selects order-item columns explicitly** —
> `.select("title,qty,unit_price_cents,total_cents")`. A new column is **invisible to the sale
> notification** until it is added there. That select is a hand-maintained set, and this is the
> class of failure the route-list rule in CLAUDE.md is about. It must move in the same change, or
> the owner's email will describe an order it cannot fully see.

## G. Cart-line identity

**Measured existing behaviour**, not assumed:

- Guest: `lineKey(pid, vid) = String(pid) + '::' + (vid || '')` (`storefront-cart.js:91`). Equal
  keys merge and `qty` accumulates — proven in 1E (Medium + Large = two lines; Medium twice = one
  line at qty 2).
- Persisted: no merge at all. Every `action:'add'` inserts a row.

**Proposal.** Extend only the guest key:

```
lineKey = pid :: (vid || '') :: canon(modifiers)
canon   = selected option ids, SORTED lexicographically, joined with ','
```

Sorting is the whole point: `{bacon, mushroom}` and `{mushroom, bacon}` are the same configuration
and must produce the same identity. **Array order is never identity.** The server computes the
identical canonical form when it validates, so client and server agree on what "the same line" is.

Leave the persisted cart's non-merging behaviour exactly as it is — changing it is a behaviour
change to a path nothing calls, and it is not what this phase was asked for.

## H. Where server-authoritative validation belongs

**One place: `_shared/commerce_checkout.ts` `computeAuthoritativeOrder`,** inside the existing
per-item loop, immediately after the variant block. It is the only function **both** checkout
paths pass through (the guest `line_items` path and the legacy `cart_id` path both call it, at
`create-store-checkout/index.ts:80` and `:102`), it already reloads the real rows, and it already
refuses with typed errors — `product_not_found`, `product_unavailable`, `variant_not_found`,
`insufficient_stock`, `invalid_quantity`. Modifier refusals are more of the same vocabulary.

**And a mirror in `commerce-api` POST `/cart`,** which must reach the same verdict — the whole
lesson of Phase 1E is that when two writers disagree about a line, the quiet one wins and the
customer pays the wrong price.

Validation the server must own (the client may send ids and nothing else): the group is attached
to *this* product; the option belongs to *that* group; both are `active`; both belong to *this*
business; required groups are satisfied; `min_select`/`max_select` hold; no duplicate option ids;
and the price delta comes from the row, never the request.

## I. The smallest additive change

- **Schema:** 3 new tables, 2 new jsonb columns (`commerce_cart_items.selected_modifiers`,
  `commerce_order_items.selected_modifiers`), both `default '[]'`. **Nothing altered, nothing
  dropped.** Every existing row is valid with zero modifiers, by default, with no backfill.
- **API:** owner CRUD for groups/options/attachment on `commerce-api` (the existing
  `/products/:id/variants` routes are the template); `/public/storefront` gains each product's
  groups and options; `/cart` add gains the same treatment `variant_id` just received.
- **Client:** `payloadToOs` maps them read-through; `store-page.js detailHtml()` renders groups
  below the existing Option select; `detailAdd()` collects the selection; `storefront-cart.js`
  extends `lineKey` / `add` / `buildLineItems`. **No new renderer, no new component file, no new
  storefront route.**
- **Checkout:** one block inside the existing loop, plus the snapshot on the existing insert.
- **Notification:** add the column to the `commerce_notify` select (see F).

## Environment facts that bind implementation

**The entire live Commerce corpus.** 2 products, both `archived`, on **1** business
(`evergreen-yard-care`, `account_kind` **test**); 0 variants; 0 cart items; 2 orders, both
`pending` test artifacts from 2026-09-06. **Zero `market` businesses have a Commerce product.**
So an additive schema change carries no live-customer exposure today — "existing products must
remain compatible with zero modifiers" is a *design* requirement here, not a migration risk.

**The migration ledger.** 168 recorded, latest `20260823130000`; **261 files on disk.**
`supabase db push` is banned and enforced by `scripts/check-no-db-push.mjs`. A new migration is
applied one at a time with `supabase db query --linked -f`, after reading it end to end.

**Two deploy paths.** Edge functions go live via `supabase functions deploy`; everything in
`public/` goes live **only** via a git push to Vercel.

## Two things found during discovery that are NOT this phase

Reported rather than absorbed, as instructed.

**1. `/inventory/apply-order` drops `variant_id` — the 1E defect's third sibling.**
`commerce-api/index.ts:775` selects `*` from `commerce_order_items` (so `variant_id` is in hand)
and then maps it away at `:779`:

```ts
items: (items || []).map((i: { product_id?: string; qty: number; title?: string }) => ({
  product_id: i.product_id, qty: i.qty, title: i.title,          // ← variant_id dropped
})),
```

The webhook caller (`commerce_checkout.ts:219`) passes it correctly. `applyOrderInventoryDeduction`
is variant-aware. So through this route, stock for a sold **Large** would be decremented from the
**parent product** while the Large variant's own count never moves. Same class as the cart defect
fixed in 1E: one variant-aware function, two callers, one blind. **Not fixed — this is inventory,
not modifiers.**

**2. There is no path from the guest cart into the persisted cart.** Nothing in `public/` ever
reads or writes `commerce_carts` / `commerce_cart_items`; the wrappers in `commerce/api.js`
(`getCart`, `addToCart`, `mergeCart`, `updateCartItem`, `removeCartItem`) have **zero callers**.
The guest cart goes straight to `create-store-checkout` with `line_items`. Phase 1F's requirement
that *"modifier selections survive moving from guest cart into persisted cart"* therefore has **no
existing path to preserve** — building one would be a new cart lifecycle, which is out of scope.
The honest version of that requirement is: **both cart representations must be able to carry a
selection, and the server must reach the same price from either.** That is testable and is what
Phase B should target.

## One decision needed before Phase B

`min_select` / `max_select` / `required` are three fields expressing two ideas — `required` is
`min_select >= 1`. Carrying both invites them to disagree, and a disagreement here is a customer
blocked from checking out or a required choice silently skipped. **Recommendation: store
`min_select` and `max_select` only, and derive `required` for display.** Raising it here rather
than deciding it silently, because it changes the schema and the schema is the part that is
expensive to change later.
